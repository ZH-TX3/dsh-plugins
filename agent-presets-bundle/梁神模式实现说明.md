## 0. 一句话概括

梁神模式是一个「**首次请求锚定**」型预设：它把模型在会话第一步看到的**工具目录收窄到 `bash` + `str_replace_editor`**，并且**不挂载两个大块自动注入插件**（技能目录 `skill-catalog`、工作区指令摘要 `agent-instructions`），以此把模型的第一条推理轨迹钉在官方 Minimal 预设的形态上；首次工具调用后一次性放开全部工具，压缩（compaction）后重新收窄。

**核心结论**：机制设计完整且自洽。曾经因 DSH 核心升级移除了 `session.events` 同步字段而**静默失效**——两处失败降级逻辑把异常吞掉了，工具收窄和指令提示双双不生效且不报警。**已于 2026-10-20 按官方规范修复**：改用 Session projection（不是被官方禁止的 `snapshotEvents()`）。第二轮分析又发现并修掉了投影方案自身的两个隐藏陷阱——共享 key 会静默覆盖折叠语义、`inject = []` 与「立刻读服务」相冲突（见 6.5）。经四层验证：真实组件（6.7）、真实历史会话回放（46→2）、以及**真实模型端到端调用**（6.8，`initial tools=2` → `change tools=46`）。

这个缺口在升级前（`0.1.1-rc.2`）是**真正生效**过的——已用真实会话日志证实（见 6.3）。

## 2. 双层装配模型（理解本预设的前提）

DSH 的插件组合分两个平面，**梁神模式只能控制其中一个**：

| 平面 | 载体 | 梁神模式能做什么 |
|---|---|---|
| **AGENT-PLANE** | `presets/liangshen.patch.yml` 的 `config.plugins` | 增删/配置本预设内的行；可用 `cordis:group` + `isolate` 建独立 realm |
| **HOST-PLANE** | `dsh-base/cordis.patch.yml` + `dsh-web-app/cordis.patch.yml` + `profiles/web/cordis.patch.yml` | 只能覆盖/禁用，或在自己的监听器里过滤其产物 |

**关键事实**：`dsh-base` 确实声明了这两个行，但 **`dsh-web-app/cordis.patch.yml` 把它们在宿主平面禁用了**：

```yaml
# dsh-base/cordis.patch.yml（基础声明）
L289  - id: agent-instructions          # AGENTS.md/CLAUDE.md 全文摘要
L304  - id: tool-skill                  # ~9KB <available_skills> 目录

# dsh-web-app/cordis.patch.yml（Web profile 的覆盖，后写生效）
L549  - id: agent-instructions
         disabled: true                 # ← 宿主平面已禁用
L487  - id: tool-skill
         disabled: true                 # ← 宿主平面已禁用
```

同处注释写明设计意图：「the base host `skill-filesystem` row is disabled here (presets own local discovery), and `tool-skill` is what a preset mounts to give its agent the catalog and loader at all」。即 **Web profile 下这两个能力由预设自己决定是否挂载**。

这带来两个直接推论，都很重要：

1. **梁神模式不挂这两行，本身就是「拔掉」，不需要靠过滤**——`tool-bootstrap` 的 `suppressedContextSources` 因此只是**纵深防御**（防止将来宿主层重新启用，或有其他插件注入同名 kind）。
2. **`standard` 预设能出现 `agent-instructions` / `skill-catalog` 注入，是因为它自己挂了这两行**；梁神模式不挂，所以真实日志里从来没有这些注入。这与过滤逻辑无关。

> 反过来看，`skill-search` 之所以必须用**新工具名**（`skill_search`/`skill_load`）而不是复用 `skill`，是因为 `tool-skill` 行（提供 `skill` 工具）在本预设里根本没挂——不存在冲突，只是纯粹的功能替代。

> 预设内 `skill-filesystem` 行（L235）是**重复声明**了宿主已有的 row id，作用是把该行注册进本预设的 scope 层，不产生新服务。

**两处刻意的「不挂载」**：没有 `agent-instructions` 行，也没有 `tool-skill` 行。

### 为什么 `tool-bootstrap` 必须排第一

这在源码注释里被称为「关键排序约束」，理由链是：

1. DSH 的 waterfall 事件（`agent/pre-step`、`system-prompt/assemble`）采用 **after-`next()` 的变换**语义：监听器先 `await next()` 拿到下游结果，再修改后返回。
2. 因此**变换实际生效顺序 = 注册顺序的逆序**：最后注册的监听器最先拿到「最终结果」，它返回什么，上游看到的就是什么。
3. 要让「剥离消息」成为**最后一道变换**（即真正能删掉别人后注入的内容），它必须**最先注册**。
4. 注册顺序由行应用顺序决定，而行应用是**并发**的（源码注释引用 issue #6 / upstream PR #13），仅靠行顺序并不够稳。所以插件还额外用了 `{ prepend: true }`：

```js
// tool-bootstrap.mjs
export const inject = []   // 故意留空

ctx.on('agent/pre-step',    handler, { prepend: true })
ctx.on('agent/request',     handler, { prepend: true })
```

`inject` 留空是**故意的**：一旦声明 `inject: ['tools']`，Cordis 会等该服务就绪才 apply，反而使本插件晚于 `dsh-agent-instructions`/`dsh-tool-skill` 注册，剥离就失效了。

## 4. 五个机制逐个拆解

### 4.1 `tool-bootstrap.mjs` —— 工具目录收窄

**配置**（patch 中的实际值）：

```yaml
- id: tool-bootstrap
  name: 'file:///C:/.../tool-bootstrap.mjs'
  config:
    bootstrapTools: [bash, str_replace_editor]
    promoteOn: tool-call
    includeSubagents: true
    suppressedContextSources: [agent-instructions, skill-catalog]
```

注意：**未设置 `bootstrapMaxTokens`**，即不限制首轮输出预算，直接沿用 adapter 默认的 256000。

**三段逻辑**：

1. **`system-prompt/assemble`** —— 收窄工具目录
   - 未晋升：`tools` 过滤为 `bootstrapTools`（若已过压缩边界，再并上 `compactionTools`）
   - 已晋升：原样返回完整目录（一步到位，无中间「常驻/发现」两段式）
   - 失败降级：`warnOnce(... exposing the full catalog ...)` 后返回完整目录 —— **宁可不锚定，也不能让会话报废**

2. **`agent/pre-step`** —— 剥离上下文注入
   - 按 `message.source.kind` 过滤，默认剥 `skill-catalog` + `agent-instructions`
   - 刻意**不**剥 `skill-invocation`（用户主动 `/skill` 触发的内容必须保留）
   - 失败降级：`warnOnce(... keeping injected context ...)` 后原样返回 —— **宁可多给上下文，也不能吃掉用户内容**

3. **`agent/request`** —— 可选的首轮输出预算上限
   - **仅当配置了 `bootstrapMaxTokens` 时才注册此监听器**（当前未配，故该监听器不存在）
   - 晋升后会显式剥掉自己设的 `maxTokens`，因为下一轮的请求 seed 会沿用上一轮 header

**失败开放（fail open）**：若 `bootstrapTools` 里某个工具在装配结果中不存在，打一次警告并**退回完整目录**，绝不因为组合漂移而锁死会话：

```
anchored-tool-bootstrap: expected every phase tool; missing=["pwsh"] — bootstrap disabled, full catalog exposed
```

**配置校验**在 `apply` 阶段（即预设挂载时）就抛错，错误信息精确可查：

```
unknown config key(s) nope — allowed keys: bootstrapMaxTokens, bootstrapTools, compactionTools, includeSubagents, promoteOn, suppressedContextSources
bootstrapTools must be a non-empty array of non-empty strings
promoteOn must be one of "tool-call", "assistant-message", "either"; got ...
suppressedContextSources must be an array of non-empty strings
bootstrapMaxTokens must be a positive safe integer
```

`suppressedContextSources: []` 是**合法**的，含义是「关掉上下文过滤，但保留工具收窄」——所以内部用 `sourceList` 而非 `stringList` 校验。

### 4.2 `compaction-epoch.mjs` —— 压缩感知的晋升状态机

压缩会把压缩前的对话塌缩成一条摘要消息，并重新注入指令基线。**压缩后的第一个请求是「第二个首次请求」**，同样的首 token 条件再次出现，所以需要重新锚定。

状态：`Map<sessionId, { boundary, promoted }>`

- `boundary`：最后一次 `compaction/end` 的 `seq`（从未压缩为 `-1`）
- `promoted`：`boundary` 之后是否存在晋升信号

```
scan(session):                        # 冷启动 / resume 重建
  boundary = -1; promoted = false
  for event of session 的事件:
      if event.type === 'compaction/end': boundary = seq; promoted = false; continue
      if event in promoteEvents and seq > boundary: promoted = true
```

`observe(session, event)`（挂在 `session/event`）做同样的增量维护，冷扫描一次后 O(1)。

**两个刻意的例外**：
- **子 agent 默认视为已晋升**：`delegationDepth > 0` 直接返回 `{boundary: -1, promoted: true}`，让子 agent 首个请求就能用工具。当前 patch 配了 `includeSubagents: true`，所以子 agent **也走锚定流程**。
- **无 agent 上下文视为已晋升**：`status(undefined)` 返回 `{promoted: true}`，避免诊断/非 agent 装配路径被误收窄。

> ⚠️ 因此预设描述里的「主/子 Agent 首轮仅 bash + str_replace_editor」是**准确**的——因为 patch 显式写了 `includeSubagents: true`。（`tool-bootstrap` 与 `instruction-hint` 两行都配了这个键。）

### 4.3 `instruction-hint.mjs` —— 用「提示存在」替代「注入全文」

**动机**：完整 AGENTS.md 摘要是大块注入，即使晋升后也持续扰动轨迹。

**做法**：不注入内容，只在**晋升后**注入一句：

```
Workspace instruction files exist: AGENTS.md, CLAUDE.local.md (project root: /repo). Do NOT assume their content. When a task touches this workspace, read the relevant instruction files first and follow them.
```

探测范围：
- 项目侧：从 `cwd` 向上走到项目根（标记 `.git` / `.hg` / `.svn`），逐层找 `AGENTS.md`、`CLAUDE.md`、`AGENTS.local.md`、`CLAUDE.local.md`
- 用户全局：`$DSH_HOME/AGENTS.md`（本机即 `<$DSH_HOME>/AGENTS.md`，1416 字节，存在）

消息形态：`{ id: 'instruction-hint-<sessionId>', role: 'user', source: { kind: 'instruction-hint', form: 'hint' } }`

**三条已验证的语义细节**：
1. **晋升后才发**，晋升前一条不发。
2. **每会话只发一次**（进程内 `hinted` Set + 持久日志扫描双保险）。
3. **压缩后不再重发**：即使 `compaction/end` 后重新回到未晋升态、随后再次晋升，也不会再发第二次。这是一个已知的行为缺口——压缩后模型不再收到「指令文件存在」的提示。

### 4.4 `skill-search.mjs` —— 用按需检索替代目录注入

`dsh-tool-skill` 会在首屏注入约 9KB 的 `<available_skills>` 目录。源码注释引用 issue #6 的实测：**带目录时锚定率 0/9，不带时约 81%**。

替代方案是「工具检索」模式，两个小工具：

| 工具 | 行为 |
|---|---|
| `skill_search` | 对 name + description + whenToUse 做子串匹配，最多 20 条摘要 |
| `skill_load` | 精确名字 → `ctx.skills.get(name, {scope, cwd, signal})` → 以 `source.kind = 'skill-invocation'` 注入全文 |

`skill_load` 注入用的 kind 是 `skill-invocation`，而 `tool-bootstrap` 默认**不**过滤这个 kind —— 两个设计刚好对齐，用户/模型主动加载的技能不会被误剥。

源码注释明确：本插件与 `dsh-tool-skill` **不能同时挂载**（会重名/重复注入）。

### 4.5 `custom-bash.mjs` —— Windows 专用 bash

`persistent-shell`（PTY 后端）在 Win32 上 `disabled: true`（DSH 的 PTY 实现仅 linux/darwin），因此 Windows 需要一个等价物。`custom-bash` 注册**同名** `bash` 工具，但走普通子进程 seam（`bash -c`），工具描述刻意写成 Minimal 兼容形态。

**Git Bash 解析链**（挂载时发现，非运行时）：

1. 显式 `config.bashPath` 或环境变量 `DSH_TUI_LIANGSHEN_BASH_PATH` → **只**用这一个候选，找不到就报错，绝不静默替换
2. 否则从 PATH 上的 `git.exe` 反推安装树（`<root>/bin/bash.exe`、`<root>/usr/bin/bash.exe`）
3. 最后回落到裸 `bash`

**WSL 启动器一律拒绝**：`C:\Windows\System32\bash.exe` 与 `C:\Windows\Sysnative\bash.exe` 会被识别并排除（它们会拉起 WSL 而非 Git Bash）。Scoop 的 `.shim` 会被跟随到真实目标。

**语义**：非零退出码不抛异常，而是把 stdout+stderr 收齐后抛 `Error(tail)`（运行时转成 `isError` 结果）；spawn 失败则是 `bash spawn failed: ...`。

> ⚠️ Windows 上**没有沙箱**（sandbox 后端仅 linux），工具描述里已写明。本机 Git Bash 在 `D:\soft\Git\bin\bash.exe`，而 bundle 里 `custom-bash` 未配 `bashPath`，依赖 PATH 上的 `git.exe` 反推。

## 5. 一个完整会话的生命周期

```
创建会话 (delegationDepth=0, agentPreset=liangshen)
  │
  ├─ status() → { boundary: -1, promoted: false }        ← 冷扫描日志
  │
  ├─ 首次 system-prompt/assemble
  │    tools 收窄为 [bash, str_replace_editor]           ← 设计意图
  │
  ├─ 首次 agent/pre-step
  │    剥掉 skill-catalog + agent-instructions 注入      ← 设计意图
  │    不发 instruction-hint（未晋升）
  │
  ├─ 模型第一次 tool/call
  │    → session/event(tool/call) → observe() → promoted = true
  │
  ├─ 下一次 assemble：返回完整 46 个工具
  ├─ 下一次 pre-step：不再剥离；发一次 instruction-hint
  │
  ├─ compaction/end (seq=N)
  │    → boundary = N, promoted = false                  ← 重新锚定
  ├─ 回到 [bash, str_replace_editor]（+ compactionTools）
  ├─ 新的 tool/call（seq > N）→ 再次晋升、再次放开完整目录
  │    （但 instruction-hint 不会重发）
  └─ ...
```

## 6. ✅ 已修复的实现缺陷（原：锚定机制实际未生效）

> **状态：已修复（2026-10-20）**。本节保留完整的问题分析作为记录；修复内容与验证结果见 6.5。

这是本次分析最重要的发现。**代码逻辑与设计意图一致，但运行时不成立。**

### 6.1 根因：`session.events` 在 DSH 0.2.0-rc.2 中不存在（0.1.x 后期就已移除）

`compaction-epoch.mjs` 第 36 行、`instruction-hint.mjs` 第 138 行都直接读 `session.events`：

```js
// compaction-epoch.mjs:36
for (const event of session.events) {
```

但 0.2.0-rc.2 的 `Session` 类（`dsh-session/lib/index.js` L1248）实际只有：

```js
var Session = class Session {
    log = [];                    // 内部字段
    header;
    inheritedEventCount;
    get id() { return this.header.id }
    get seq() { ... }
    snapshotEvents(fromSeq, toSeqExclusive) { ... }   // ← 公开读接口
    ownEvents() { ... }
    requestHeader() { ... }
}
```

**没有 `events` 成员**。全包树 `grep session.events` 在第一方代码中零命中（只有本 bundle 的模块在用）。这是从旧版 DSH API 迁移时遗漏的改名。

### 6.2 后果：两条降级路径把故障「吃掉」了

两个插件都实现了「失败降级」，恰好把 `TypeError` 静默吞掉：

**`tool-bootstrap`**（`system-prompt/assemble` 的 catch）：

```
anchored-tool-bootstrap: bootstrap filter failed, exposing the full catalog: session.events is not iterable
```

→ 返回**完整 46 个工具**，工具收窄从未发生。

**`instruction-hint`**（`agent/pre-step` 的 catch）：

```
instruction-hint: hint injection failed, skipping: session.events is not iterable
```

→ 提示从不注入。

而 `agent/pre-step` 的**上下文剥离**用的是同一个 `promotion.status(agent)`，同样抛错、同样被 catch 成「保留全部上下文」：

```
anchored-tool-bootstrap: pre-step context filter failed, keeping injected context: session.events is not iterable
```

### 6.3 时间线证据：锚定曾经是好的，在 0.2.0 升级后坏掉

扫描 `~/.dsh/sessions/` 下**全部**会话，取每个会话首个 `request/header` 的工具数：


### 6.4 正确的修复方式：Session projection（不是换成 snapshotEvents）

**这一步很关键，走错过一次。**

第一版修复把 `session.events` 改成了 `session.snapshotEvents()`——能跑，但**违反官方治理规则**。查官方 Agent Note 后确认：

> `.agents/notes/implemented/architecture/2026-09-09-deprecate-synchronous-session-event-reads.md`
>
> - `Session.eventAt()`、`Session.snapshotEvents()`、`Session.ownEvents()` **全部已弃用**。
> - "Existing logic may remain unmigrated for now, but **new calls are prohibited**. **New aliases or wrappers that expose the same synchronous historical access are prohibited as well.**"
> - 迁移方向：「Design durable event fields and Session projections together so each domain can reconstruct the state its consumers need. Restore that state during resume, then maintain it incrementally from newly committed events.」

也就是说，我最初写的 `const eventsOf = (session) => session.snapshotEvents()` 这种「包装器」被**点名禁止**。

**官方正解**是注册一个 Session projection unit，用 `ctx.sessionProjections.stateOf(session, key)` 同步读取已经折叠好的状态。配套 note：

> `.agents/notes/implemented/architecture/2026-08-19-session-projection-mandatory-seam.md`
> 「Every host reader treats the projection registry and its required key as mandatory state… it never degrades to a default value.」

`dsh-session-projection` 在 `dsh-base/cordis.patch.yml` L158 已被官方挂载，所以预设可以直接用。

**实现要点**（`compaction-epoch.mjs`）：

```js
export const epochProjectionKey = (promoteEvents) =>
  `liangshen-epoch:${[...new Set(promoteEvents)].sort().map(t => t.replace('/', '-')).join('+')}`

export const createEpochProjection = (promoteEvents) => ({
  key: epochProjectionKey(promoteEvents),   // 按语义派生，理由见 6.5
  stateSchema: { parse(v) { /* 校验 {boundary, promoted, hinted} */ } },
  stateVersion: 1,
  init: () => ({ boundary: -1, promoted: false, hinted: false }),
  apply(state, event) {
    const seq = event.seq ?? 0
    if (event.type === 'user/message' && event.data?.source?.kind === 'instruction-hint')
      return state.hinted ? state : { ...state, hinted: true }
    if (event.type === 'compaction/end')
      return { boundary: seq, promoted: false, hinted: state.hinted }
    if (promote.has(event.type) && seq > state.boundary && !state.promoted)
      return { ...state, promoted: true }
    return state          // 同一引用 → 官方保证零下游开销
  },
})
```

三个设计细节值得记下：

1. **`hinted` 并入同一个 unit**。原本 `instruction-hint` 要扫历史找「是否已发过 hint」，现在由 `apply` 折叠；这样 resume 判断也不需要历史扫描。
2. **`hinted` 不随压缩重置**——hint 语义是「每个会话一次」，不是「每个 epoch 一次」（与 4.3 描述一致）。
3. **registry 缺失时直接抛错**，不回退到扫描历史。这符合 note 的 "never degrades to a default value"。原来的实现是 fail-open 静默降级，正是它把本次缺陷藏了一个月。

同时**移除**了 `ctx.on('session/event', …)` 订阅：registry 已经 eager 驱动每个已注册 unit，手动 `observe()` 是多余的。


### 6.5 投影方案的两个隐藏陷阱（第二轮分析发现并修复）

把「扫历史」换成「读投影」之后，又暴露出两个**只有仔细读官方实现才会发现**的坑。两个都属于「默认配置下侥幸不出事，一旦配置改动就静默出错」的类型。

#### 陷阱一：同一个 key 被两个插件共享 → 折叠语义被静默覆盖

`tool-bootstrap` 和 `instruction-hint` 都会 `createEpochPromotion(...)`，最初两者都用同一个常量 key `liangshen-epoch`。

看 `dsh-session-projection/lib/index.js` 的 `register()` 实现：

```js
const existing = this.registrations.get(key)
if (existing === undefined) this.registrations.set(key, { def: erased, cells: new WeakMap(), refs: 1 })
else {
  if (existing.def.stateVersion !== erased.stateVersion) throw new Error(`... refusing to share it ...`)
  existing.refs += 1        // ← 只计数，完全不管 apply 语义是否相同
}
```

**同 key 注册只比较 `stateVersion`，不比较折叠语义**；后注册者的 `apply` 被直接丢弃，`refs` 加一了事。而两个插件的 `promoteOn` 是**各自独立配置**的：

| 插件 | 默认 `promoteOn` |
|---|---|
| `tool-bootstrap` | `tool-call` |
| `instruction-hint` | `either` |

当前 preset 里两者都显式写了 `promoteOn: tool-call`，所以**恰好**一致、不出事。但只要有人只改其中一个（比如给 hint 放开成 `either`），`tool-bootstrap` 就会拿到 `either` 的语义——纯文本回复也会解锁全量工具目录，锚定失效且**没有任何报错**。这与最初那个 bug 是同一类失败模式。

**修复**：key 由折叠语义派生，而不是共用常量。

```js
export const EPOCH_PROJECTION_KEY_PREFIX = 'liangshen-epoch'

export function epochProjectionKey(promoteEvents) {
  const suffix = [...new Set(promoteEvents)].sort().map(t => t.replace('/', '-')).join('+')
  return `${EPOCH_PROJECTION_KEY_PREFIX}:${suffix}`
}
// → "liangshen-epoch:tool-call"
// → "liangshen-epoch:assistant-message+tool-call"
```

排序后再拼接，保证同一语义集合在不同进程里得到**同一个** key（投影缓存按 key 持久化，key 必须跨进程稳定）。

#### 陷阱二：`inject = []` 与「立刻读服务」冲突

`tool-bootstrap` 的 `inject = []` 是**刻意设计**（源码注释有说明）：不注入才能保证它排在 `dsh-agent-instructions` / `dsh-tool-skill` 之前注册，从而在 waterfall 里成为**最后**一个变换，把首轮注入的上下文真正剥掉。

但投影方案需要在 `apply()` 里拿到 `sessionProjections` 服务。我最初写的是：

```js
const registry = ctx.get('sessionProjections')
if (registry === undefined) throw new TypeError(...)
```

这在实测中能跑通，但**依赖加载顺序**——`session-projection` 在 `dsh-base/cordis.patch.yml` L158 挂载，恰好排在预设之前。一旦顺序变化，插件会在服务就绪前抛错，整个预设加载失败。

官方注释给了正确做法：

> A host reader either declares `sessionProjections` in its plugin `inject` or fails explicitly when the registry or required key is absent. Contributors may preserve optional registration through `ctx.inject(['sessionProjections'], ...)`.

即：**不要动插件的 `inject` 列表，改用 `ctx.inject([...], cb)` 延迟注册**。这样既不破坏 `inject = []` 的排序保证，又能等服务就绪。

```js
ctx.inject(['sessionProjections'], (scope) => {
  const service = scope.get('sessionProjections')
  if (service === undefined) throw new TypeError(`${key}: the sessionProjections registry is required …`)
  registry = service
  service.register(projection)   // 注册是 scope fiber 上的 effect，随其销毁
  settle()
})
```

配套改动：`status()` / `hinted()` 在服务未挂载前返回「未晋升 / 未发过 hint」而不是抛错；两个消费方在 `await next()` 之后 `await promotion.ready()`，确保首个请求读到的是已注册的投影，而不是「服务还没好」的假象。

**为什么不能简单地 `inject = ['sessionProjections']`**：那会让 Cordis 等到该服务就绪才 `apply()`，从而把本插件排到宿主 `agent-instructions` / `tool-skill` 之后注册，首轮上下文剥离就不再是最后一个变换——锚定机制的核心前提被破坏。

#### 验证

| 场景 | 结果 |
|---|---|
| 两个插件用**不同** `promoteOn` 注册 | key 不同，互不干扰；`tool-call` 单元不因 `assistant/message` 晋升，`either` 单元会 ✓ |
| 同语义、不同书写顺序 | 得到同一 key（缓存可命中）✓ |
| 服务**延迟**就绪 | 就绪前 `status()`/`hinted()` 安全返回默认值，就绪后立即读到正确投影 ✓ |
| 服务**始终缺席** | 仍然显式抛错，不静默降级 ✓ |
| 完整行为回归（13 项） | 冷启动 2 个工具 / `tool/call` 后 7 个 / 压缩后回到 2 个 / hint 仅一次 / resume 不重发 ✓ |
| `dsh --profile web` 真实启动 | 无 `did not activate`、无 `waiting for service`、无 fail-open 警告 ✓ |

```js
function assertAdoptable(header, events, sessionId, cwd) {
  const preset = currentPreset(header, events, sessionId)
  if (preset !== void 0) throw new Error(
    `session "${sessionId}" runs under agent preset "${preset}", which the one-shot runner does not compose`)
  ...
}
```

`dsh-headless` 的 `agents.create()` 不经过 `agentPresets` 组合，所以一次性运行器根本不支持 preset。之前那次「headless 跑通但 `preset: (none)`、24 个工具」正是这个原因——**不是配置错误，是设计边界**。

#### 正确做法：在 web profile 宿主进程内驱动

用 DSH 自己的 `runProfile()` 引导真实 web profile，再走 Web UI 同一条入口
`sessionController.agents.ensureSession(sessionId, cwd, isNew, agentPreset)`：

```js
const { ctx } = await runProfile({ profile: 'web', environment: loadLayeredEnv('dsh'), args: [...] })
const sc = ctx.get('sessionController')
const agent = await sc.agents.ensureSession(sessionId, cwd, false, undefined)
// header.agentPreset === 'liangshen'，投影 agentPreset === 'liangshen'
await sc.prompt({ sessionId, requestId, content: [{ type: 'text', text }] }, signal)
await agent.whenIdle()
```

两个坑值得记下：

1. **`environment` 不能手搓**。我第一次传了个 `Map`，结果 `launchEnvironmentOf(...).getFrom is not a function`，模型请求直接失败。必须用官方的 `loadLayeredEnv('dsh')`。
2. **`prompt()` 需要第二个 `signal` 参数**，否则 `Cannot read properties of undefined (reading 'throwIfAborted')`。

#### 结果：真实会话的完整曲线

真实工作区（含 `AGENTS.md` + 一个 `add` 写成减法的 `calc.py`），真实模型 `workbuddy/deepseek-v4.1-flash-sg`：

```
preset: liangshen
  seq=12  reason=initial  tools= 2  ["bash","str_replace_editor"]     ← 锚定生效
  seq=22  reason=change   tools=46  ["advanced_search", ..., "write"]  ← 首次 tool/call 后晋升
tool/call count: 8
user sources: user,time-context,instruction-hint,skill-invocation
```

四项关键结论**全部在真实模型上得到证实**：

| 机制 | 证据 |
|---|---|
| 首轮工具收窄 | `reason=initial` 只有 2 个工具 |
| 首次工具调用后放开全量 | `reason=change` 变成 46 个 |
| 上下文剥离 | `user sources` 里**没有** `agent-instructions` / `skill-catalog` |
| instruction-hint 注入 | `user sources` 里出现 `instruction-hint` |

模型的真实行为也符合设计意图：拿到 2 个工具后先用 `bash` 探索（`ls`、读 `AGENTS.md`、跑命令），**先摸清环境再动手**，而不是一上来就在 46 个工具里挑。

## 7. 其他已知事项

| 项 | 说明 |
|---|---|
| **persona `complete` 已补回** | 官方 Minimal 用 `prefix + complete: true + includeRuntimeContext: false`；梁神模式原本**只有后两个**，导致首屏 system prompt 仍包含 Harness 身份与全部工具指引（真实日志 10037 字符，以 `You are an AI agent powered by DeepSeek Harness.` 开头）。`dsh-persona` 0.2.0-rc.2 支持 `complete?: boolean`，判断为迁移时误删，**已补回**（同时同步到 profile 副本）。 |
| **`tool-web` 关闭了 fetch** | `fetch: false`，所以只有 `web_search` 没有 `web_fetch`，web 段落走「只返回摘要」分支。 |
| **无沙箱（Windows）** | sandbox 后端仅 linux，`custom-bash` 的工具描述已声明无隔离。 |
| **RTK 集成已移除** | `custom-bash.mjs.bak-pre-rtk` 与当前文件 **byte 级一致**，说明 2026-10-19 摘掉 RTK 包装后未再改逻辑。原因记录在源码/笔记：RTK 改变了 bash 输出形态，反而扰动推理轨迹。 |
| **hint 不随压缩重发** | 见 4.3，这是**有意设计**：hint 语义是「每会话一次」。修复后由投影的 `hinted` 字段保证，且刻意不随压缩重置。 |
| **两个 router 预设同源同修** | `modules/router-standard/` 与 `modules/router-spec/` 的 `router-core.mjs`、`router-bootstrap-v1.mjs` 有相同缺陷，已一并改为 projection 方案。这也解释了 10-19 之后 `router-standard` 会话为何也不再锚定（该 preset 当前在 profile 中 `disabled: true`，影响有限）。 |
| **`router-standard` / `router-spec` 的 core 完全相同** | 两个 `router-core.mjs` 字节一致，差异只在 patch 声明。 |
| **全部机制已在真实模型上验证** | 见 6.8：真实 `workbuddy/deepseek-v4.1-flash-sg` 会话产生 `initial tools=2` → `change tools=46`，8 次真实工具调用，`user sources` 含 `instruction-hint` 且不含 `agent-instructions`/`skill-catalog`，无 fail-open 警告。模型行为也符合预期：先 `bash` 探索再动手。 |

## 8. 如何改这个预设

1. 改 `presets/liangshen.patch.yml`（行定义）或 `modules/liangshen/*.mjs`（行为）。
2. 三者择一让改动生效：
   - Web 端「插件」页面保存（会写回 profile patch，覆盖同 id 行）
   - 直接改 `profiles/web/cordis.patch.yml`
   - 重装 bundle（`profiles/web/package.json` 里是 `"@local/dsh-agent-presets": "file:../../agent-presets-bundle"`）
3. **排序约束别动**：`tool-bootstrap` 必须保持第一个，且保持 `inject = []` + `prepend: true`。
4. 改完自测：至少验证「首轮 `request/header` 的工具数」与「是否出现 fail-open 警告」，否则锚定是否生效无从判断。

### 验证锚定是否真的生效

```bash
# 看某个 liangshen 会话首个请求的工具数（应为 2，不是 46）
# 见本文分析脚本：解压 session.v4.jsonl.zstd 的 zstd 帧序列，
# 取首个 request/header 的 header.tools.length
```

或在 Web UI 里看日志是否有 `bootstrap filter failed` / `hint injection failed` 警告——修复后**不应再出现**（旧版因 `session.events` 抛错被 fail-open 吞掉而必然出现）。
